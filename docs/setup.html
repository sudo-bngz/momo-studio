Setup & deploy

The app keeps no database of its own: everything lives in GoHead, and the app talks to it as you. So the setup is really two things — a GoHead with the studio's content model pushed into it, and this app pointed at it.

Install and run

You need Node.js 20.9 or newer, and Docker to run GoHead locally.

git clone https://github.com/sudo-bngz/momo-studio.git studio-manager
cd studio-manager
cp .env.example .env.local
npm install
docker compose pull    # once, and whenever you move GoHead forward
docker compose up -d   # GoHead (API + admin) on :8080
npm run gohead:setup   # model + types + the studio-staff role and feed secrets
npm run gohead:seed    # optional: a sample studio
npm run dev

Open http://localhost:3000 and sign in with admin / gohead-local-password — the defaults in docker-compose.yml. Change them before this is reachable from anywhere but your laptop.

Your own studio instead of the sample

Skip npm run gohead:seed and start empty. The order that saves the most work:

  1. Rooms and locations first — the racks, desks and stands you'll put things in.
  2. The machines. Fill the ports from a template where there is one; the Allen & Heath GS3 24/8/2 fills 163 ports, correctly named. Templates live in src/lib/templates/devices.json — add your own gear there.
  3. The patchbays, with each column's mode set to match the hardware.
  4. The cables. If the patch already lives in a spreadsheet, paste it a column at a time into the patchbay and console boards rather than typing it again.

Steps 1 and 2, from a file

Typing twenty-odd machines into a form is the worst hour of this. gohead/inventory.json is your studio as an editable list — rooms, the places in them, and one line per machine — and one command creates whatever is in it:

npm run studio:bootstrap -- --dry-run   # what it would create
npm run studio:bootstrap                # create it

A line names a template and the machine arrives with every socket already on it, from the same expander the app's Fill the ports button uses — so a template fix reaches both at once. Matching is by the device code, so adding a line and running it again creates only what is missing; it never edits or deletes what is already there. Rename a machine, move it, repatch it, add ports by hand — a later run leaves all of it alone. --dry-run checks the file against gohead/model.json first, so a misspelt field is a message about the file rather than a half-created studio, and -- --file other.json runs a different one.

-- --fill-ports is the one exception, and it is opt-in. A machine created before its template existed sits there with an empty port list; with the flag, a machine whose ports are empty and whose line names a known template gets them. Anything with even one port is left alone, so the flag cannot overwrite work. Without it, those machines are simply listed at the end of the run.

Mark anything you are unsure of with "check": true and the run lists it at the end, under worth a look at the back panel before you trust the ports. Cables are deliberately not in the file: the patch is what changes weekly, and it belongs in the app where the plan can check it.

Scripts

npm run dev
The app, in development, on :3000.
npm run build / npm start
A production build, and serving it.
docker compose up -d
GoHead itself, API and admin, on :8080, with its data in a named volume.
npm run gohead:setup
The usual one: pushes the model, regenerates the TypeScript types, creates the roles and the calendar feed's secrets. Run it after every git pull that changed the model.
npm run gohead:push
Just the model — gohead/model.json, the collections and components the app reads.
npm run gohead:types
Regenerates src/gohead.d.ts from the model, so the app stops compiling when the two disagree.
npm run gohead:seed
Loads gohead/seed.json: the sample studio.
npm run studio:bootstrap
Creates the studio in gohead/inventory.json — rooms, places and machines with their ports filled from the templates. Idempotent by device code, and it never edits what is already there; -- --dry-run first, -- --fill-ports to give ports to a machine that has none.
npm run gohead:access
Creates the studio-staff role, the read-only calendar-feed role, its token and the calendar URL's secret. With -- --user alex it also creates a person and prints their password once.
npm run docs
Rebuilds this site from src/lib/help/en.ts.
npm run lint / typecheck
What CI would run.

Environment

GOHEAD_URL
Where GoHead is, as this server reaches it. Defaults to http://localhost:8080.
GOHEAD_HOSTPORT
Set by the Render blueprint from the CMS service's private address; used when GOHEAD_URL is unset, so the two services talk over the private network.
GOHEAD_FEED_TOKEN
A read-only API token for the calendar feed. Written by npm run gohead:access.
STUDIO_ICS_SECRET
The ?key= in the calendar URL. Also written by that script.
STUDIO_TZ
The studio's time zone, for the calendar and the booking grid. Defaults to Europe/Paris.

The app never holds a GoHead admin password. Each person signs in as themselves and the app keeps that person's own GoHead token in an httpOnly cookie, which is what makes the activity trail say who did what.

Subscribing to the calendar

After npm run gohead:access, .env.local holds STUDIO_ICS_SECRET. Subscribe to:

https://<your-app>/bookings.ics?key=<STUDIO_ICS_SECRET>

It's read-only and one way: it shows your sessions in your calendar, it doesn't take events back. Google refreshes an external calendar on its own schedule, often hours — fine for the week in your pocket, not for a change you just made.

Deploying to Render

render.yaml in the repo is a blueprint for two services: GoHead with a disk for its data, and this app. They talk over Render's private network, so no token ever leaves it.

  1. Push the repo to your own GitHub account.
  2. In Render: New → Blueprint, pick the repo, apply.
  3. Set GOHEAD_USERNAME and GOHEAD_PASSWORD on the CMS service only — not on the app, so that a compromise of the app doesn't hand over admin.
  4. Once it's up, run gohead:push and gohead:access against it with GOHEAD_URL pointing at the CMS's URL.

The CMS service must be on a paid plan: Render's free services can send private-network requests but not receive them, and the app needs to reach the CMS.

When GoHead restarts every minute: unknown command "standalone"

Error: unknown command "standalone" for "gohead"
2026/10/22 20:12:34 Error executing command: unknown command "standalone" for "gohead"

The image is older than GoHead v0.6.0, which is where standalone landed. docker compose up -d reuses a tag it has already pulled without asking the registry, so an image fetched before then keeps starting the old binary — and restart: unless-stopped turns that into a loop, one restart a minute.

docker compose pull && docker compose up -d
docker compose logs -f gohead

docker-compose.yml pins the minor (0.7), so a fresh clone can't land in this; docker compose pull moves it forward, and GOHEAD_VERSION=0.8 docker compose up -d picks another line. If gohead is a binary on your PATH rather than the container, it's the same cause — gohead version tells you what you have.

When npm install fails with UNABLE_TO_GET_ISSUER_CERT_LOCALLY

That's TLS interception — a corporate proxy or a security agent re-signing HTTPS with its own root. macOS trusts that root, Node doesn't, so the browser works and npm doesn't. Nothing in this repo needs changing. Either:

# Node 22.15+ / 24+: trust the system keychain
NODE_OPTIONS=--use-system-ca npm install

# or point Node at the proxy's root certificate
NODE_EXTRA_CA_CERTS=/path/to/corporate-root.pem npm install

Don't reach for strict-ssl=false: it turns off the check instead of fixing it.

Content model

gohead/model.json is the whole thing. Collections: rooms, locations, devices, cables, maintenance, clients, bookings. Components: port, patch_point, channel_strip. Cables point at a device and a port by name, which is why renaming a port that a cable uses is refused.

Change the model and push it with npm run gohead:push; add -- --dry-run first to see what it would do, and -- --allow-removals when you really mean to drop a field.
